# /tickets-from-updates

Arguments: `$ARGUMENTS` = a project name from `.claude/project-map.md` or "all", an optional window (a number of days back, or an ISO date), optionally `dry-run`.

Read first: `.claude/project-map.md`, `.claude/reference/ticket-rules.md` (including the Standing rulings). Credential notes are skipped by change detection and read only when a ticket needs credentials.

## Golden rule
Never touch a ticket in Done or QA (see `ticket-rules.md`). Do not link, relate or reparent new tickets to a Done or QA ticket. If a Done or QA ticket already covers a change, report it and propose nothing.

## Steps
1. **Find what changed.** For each project run `python3 .claude/scripts/changed_notes.py --project "<folder>"` (add `--since <window>` if a window was given). The script is read-only and ignores digest folders, folder `CLAUDE.md` files and sensitive notes. Without `--since` it compares content hashes against the recorded baseline, so touched-but-unedited notes are skipped. With `--since` it simply lists notes modified in that window (no hash comparison), so state which mode you used. Undecided items in the notes are skipped, not proposed. If it prints `NO BASELINE`, ask the user whether to use a window (`--since`) or record today's state as the baseline (`--record`, which writes only `.claude/state/last-processed.json`). Never flood the run with every note.
2. **Read only the changed notes**, plus the project's start notes and the newest dated notes for context. Note when a changed note supersedes an older one.
3. **Freshness sweep, then decide what deserves a ticket.** Do the sweep in `project-map.md` (changed notes are only one source; the latest calls and Slack often hold newer decisions) and say what you read. **Decide what deserves a ticket.** Extract decisions, new requirements, scope changes, bugs and blockers. Ignore chatter, brainstorming, notes-to-self and anything not yet decided. Group related changes into one proposal per outcome.
4. **Choose the template** for each group using the rules in `ticket-rules.md`. Related changes across several feature areas become one proposed epic plus child standard tickets. A single outcome becomes one standard ticket.
5. **Conflict check** for every group, as in `ticket-rules.md`. **The conflict check always cross-references three groups in the same area: Done tickets, QA tickets and Backlog/To-do tickets.** Read each one's description in full (not titles), name the covering ticket, and classify the open ticket as built (propose closing it as Canceled, with a comment on the open ticket only), partly built (rewrite it down to what is missing), conflicting (state the conflict, never pick a side) or still needed. Done and QA tickets are read-only. See `ticket-rules.md`, Conflict check step 0. Existing tickets that should be rewritten rather than recreated become proposed updates (to be done with `/update-ticket`). Conflicts the notes cannot settle go under Open questions with a drafted Linear comment for dev. Run the Hierarchy check in `ticket-rules.md` for each affected parent and epic.
6. **Ask the PM the product questions first** (one at a time; see `ticket-rules.md`), then **draft** up to five of the highest-value new tickets in full, product-focused, no technical detail, each sized to its change (a larger change may carry a slightly longer context) with short, plain Expected behaviour (see "Quality bar" in `ticket-rules.md`). Add the optional Credentials section only where a ticket needs it. Save each to a scratch file in the session scratchpad and run the check script from the vault root. Fix every FAIL. List any further proposals as one-line titles and draft more only when the user picks them. Notes that are themselves draft tickets (often in an older format, marked "drafts only") are proposals awaiting the user's go: list them, and convert only the ones the user chooses. Items that fit neither DEV nor DES are listed as "not a DEV/DES ticket" and not drafted. Anything that depends on an unconfirmed client answer is held and listed, and no separate testing or audit tickets are proposed (Standing rulings). The check script also lists every ticket ID in a draft: run `get_issue` on each and replace any Done or QA ID with a plain description of the finished work.
7. **Present a short batch summary**: proposed new tickets (title, template, team, parent), proposed updates to existing tickets, decisions that already have a ticket and need no action (name the ticket), parents or epics made stale by the batch (the Hierarchy table), proposed vault note updates if the changes show project-level context that is missing or superseded, and anything skipped with a one-line reason. Show the full drafts on request. If `dry-run`, stop here and say nothing was created or recorded.
8. **Wait for a clear yes**, ticket by ticket or as a named batch.
9. **Create only what was approved.** Re-run the check on the exact text, then `save_issue` (prompts; intended). Send the `## <title>` line's text as `title` and leave that line out of `description`, so the title is not printed twice in the ticket (see `ticket-rules.md`). Report IDs and URLs. Do not set phase labels.
10. **Record the marker last.** Only after the approved tickets exist, run `python3 .claude/scripts/changed_notes.py --project "<folder>" --record`. If the user approved nothing, ask whether to record anyway; the default is not to, so the notes show up again next time.

Never create a ticket without step 8.
