# /tickets-from-updates

Arguments: `$ARGUMENTS` = a project name from `.claude/project-map.md` or "all", an optional window (a number of days back, or an ISO date), optionally `dry-run`.

Read first: `.claude/project-map.md`, `.claude/reference/board-sweep.md` (the Todo rule), `.claude/reference/ticket-rules.md` (including the Standing rulings). Credential notes are skipped by change detection and read only when a ticket needs credentials.

## Golden rule
Never touch a ticket in Done or QA (see `ticket-rules.md`). Do not link, relate or reparent new tickets to a Done or QA ticket. If a Done or QA ticket already covers a change, report it and propose nothing.

Only the PM's own tickets are edited (Ownership rule in `ticket-rules.md`). Never propose a change to a ticket created by someone else. Read `createdBy` on any existing ticket that overlaps a change and report it to the PM as "flag only".

## Steps
1. **Find what changed.** For each project run `python3 .claude/scripts/changed_notes.py --project "<folder>"` (add `--since <window>` if a window was given). The script is read-only and ignores digest folders, folder `CLAUDE.md` files and sensitive notes. Without `--since` it compares content hashes against the recorded baseline, so touched-but-unedited notes are skipped. With `--since` it simply lists notes modified in that window (no hash comparison), so state which mode you used. Undecided items in the notes are skipped, not proposed. If it prints `NO BASELINE`, ask the user whether to use a window (`--since`) or record today's state as the baseline (`--record`, which writes only `.claude/state/last-processed.json`). Never flood the run with every note.
2. **Read only the changed notes**, plus the project's start notes and the newest dated notes for context. Note when a changed note supersedes an older one.
3. **Freshness sweep, then decide what deserves a ticket.** Do the sweep in `project-map.md` (changed notes are only one source; the latest calls and Slack often hold newer decisions) and say what you read. **Decide what deserves a ticket.** Extract decisions, new requirements, scope changes, bugs and blockers. Ignore chatter, brainstorming, notes-to-self and anything not yet decided. Group related changes into one proposal per outcome.
4. **Choose the template** for each group using the rules in `ticket-rules.md`. Epic-led: related changes across several feature areas become one proposed epic (or an update to an existing epic), not a pile of child tickets; devs create the tasks. A single small outcome becomes one standard ticket.
5. **Conflict check** for every group, as in `ticket-rules.md`. **The conflict check always cross-references three groups in the same area: Done tickets, QA tickets and Backlog/To-do tickets.** Read each one's description in full (not titles), name the covering ticket, and classify the open ticket as built (propose closing it as Canceled, with a comment on the open ticket only), partly built (rewrite it down to what is missing), conflicting (state the conflict, never pick a side) or still needed. Done and QA tickets are read-only. See `ticket-rules.md`, Conflict check step 0. Existing tickets that should be rewritten rather than recreated become proposed updates (to be done with `/update-ticket`). Conflicts the notes cannot settle go under Open questions with a drafted Linear comment for dev. Run the Hierarchy check in `ticket-rules.md` for each affected parent and epic.
6. **Ask the PM the product questions first** (one at a time; see `ticket-rules.md`), then ask the set-up questions for each proposal (Set-up questions in `ticket-rules.md`; ask once for a group when the answers would be the same, naming its tickets), then **draft** up to five of the highest-value proposals in full (epics first), product-focused, no technical detail, in simple, user-focused wording with Requirements a user could try (API tickets name the endpoints only). Under Dependencies, `Blocked by:` lists open tickets only, each also set as a Linear blocked-by link (never a Done or QA ticket; never create a circular chain: check the proposed blocker's own blockers first). Client and partner decisions go under `Waiting on:`. Todo means certain (see `board-sweep.md`): raise a ticket in Todo only if a developer can finish it with no blockers AND it is definitely needed with final requirements. Anything waiting on a client or partner decision is raised in Backlog. If it is not needed soon, propose priority Low. Add the optional Credentials section only where a ticket needs it. Save each to a scratch file in the session scratchpad and run the check script from the vault root. Fix every FAIL, and any "NOTE: old template" line (it means the draft used the wrong headings). List any further proposals as one-line titles and draft more only when the user picks them. Notes that are themselves draft tickets (often in an older format, marked "drafts only") are proposals awaiting the user's go: list them, and convert only the ones the user chooses. Items that fit neither DEV nor DES are listed as "not a DEV/DES ticket" and not drafted. Anything that depends on an unconfirmed client answer is held and listed, and no separate testing or audit tickets are proposed (Standing rulings). The check script also lists every ticket ID in a draft: run `get_issue` on each and replace any Done or QA ID with a plain description of the finished work.
7. **Present a short batch summary**: proposed new tickets (title, template, team, parent, and the set-up answers: status, priority, labels and assignee, each marked as chosen, accepted or left blank), proposed updates to existing tickets, decisions that already have a ticket and need no action (name the ticket), parents or epics made stale by the batch (the Hierarchy table), proposed vault note updates if the changes show project-level context that is missing or superseded, and anything skipped with a one-line reason. Show the full drafts on request. If `dry-run`, stop here and say nothing was created or recorded.
8. **Wait for a clear yes**, ticket by ticket or as a named batch.
9. **Create only what was approved.** Re-run the check on the exact text, then `save_issue` (prompts; intended). Send the `## <title>` line's text as `title` and leave that line out of `description`, so the title is not printed twice in the ticket (see `ticket-rules.md`). Read each ticket back and report its ID, URL and the status, priority, labels, assignee and parent as returned (`ticket-rules.md`, Hardening before any write, step 6). Do not set phase labels.
10. **Record the marker last.** Only after the approved tickets exist, run `python3 .claude/scripts/changed_notes.py --project "<folder>" --record`. If the user approved nothing, ask whether to record anyway; the default is not to, so the notes show up again next time.

Never create a ticket without step 8.
