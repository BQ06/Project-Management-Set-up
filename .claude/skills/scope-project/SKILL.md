# /scope-project

Arguments: `$ARGUMENTS` = a project name, optionally `new` or `replan`, optionally `dry-run`.

Read first: `.claude/project-map.md`, `.claude/reference/ticket-rules.md` (including the Standing rulings), `.claude/reference/vault-update-rules.md`. Phase labels are applied only by this skill. Credential notes are not inputs here.

## Cross-check
Before placing any ticket in a phase, cross-reference Done, QA and Backlog/To-do tickets in the same area as in `ticket-rules.md` (Conflict check step 0): a Backlog ticket whose behaviour is already built is flagged as redundant, not phased, and a Done or QA ticket is never relabelled.

## Golden rule
Never touch a ticket in Done or QA (see `ticket-rules.md`). Phase labels, re-statusing and any other write skip them, even when their phase label looks wrong: list them in the proposal as "flagged, not changed".

Only the PM's own tickets are edited (Ownership rule in `ticket-rules.md`). Read `createdBy` on every ticket before a label or status write. Tickets created by someone else are skipped and listed as "flagged, not changed".

## Two modes
- **new** (before build): inputs are requirements only: a draft contract, SoW, client brief, or the user's notes. No tickets, labels or drift exist. Do not read Linear tickets except to confirm there are none.
- **replan** (during build): adds Linear (tickets, statuses, phase labels) and the newest dated notes, and checks the plan against them.
If the mode is not given, say which you detect and why, and let the user correct it.

## Steps
1. **Project and first-run interview.** If the project is not in the project map, interview the user one question at a time. Read the notes and Linear first and ask only what they cannot answer: vault folder, Linear project (if one exists), who leads the plan (team-led, or client-led where the plan starts as a proposal to the client), which method orders the phases (MoSCoW, build order or client priority), and which start notes to use (include the project folder's own `CLAUDE.md` if there is one). These are two separate settings: `Led by` and `Ordering method`. Show the proposed project-map entry and write it to `.claude/project-map.md` only after a clear yes. A project already in the map skips the interview, except that if `Led by` or `Ordering method` is "not yet set" you ask those questions and offer to update the map.
2. **Freshness sweep first.** Do the sweep in `project-map.md` (Linear fresh, the last 30 days of Granola meetings, Slack, newest notes, the stale check) and open your answer with what you read and as of when. Then **read the inputs.** Start with the start notes in the project map and any notes the user names. Then use the other context sources in the project map: the project's Slack channels (recent messages, newest first), any client-facing document such as the client roadmap, and the project's wireframe or design artifact. A client-facing roadmap records what the client has been told, so compare the plan with it and flag differences in scope, order or dates. Read more only when a requirement points to it, and say which notes you used. A note marked superseded is context only: say so and do not take its order or decisions. Group requirements by outcome, user journey or role, and mark each:
   - **decided:** the client or user confirmed it, or a later dated note settles it.
   - **proposed:** suggested by us or still in a draft.
   - **unknown:** open, unconfirmed, or contradicted by another note.
   When notes contradict each other, a version counts as decided only if a later dated note or the user says so. Otherwise mark it unknown and put both versions in Open questions. Never pick one.
   A note that says a decision is made "in principle" or "pending sign-off" counts as proposed until it is signed off: use it, and put what it changes in Open questions.
   Say "build phase N" for this project's phases and "later product phase" for notes that use "phase" to mean future products, so the two are never confused.
   In `new` mode use requirement-level content only. Ignore ticket IDs, build status and progress updates found in the notes. If the notes are mostly post-build, say so and suggest `replan`. Do not read Linear in `new` mode; ask the user whether any tickets already exist.
   Do not invent anything. Request only the Linear fields and labels you need, so large outputs stay readable.
   **An existing plan is the baseline.** If the project already has a plan (a `Scope and Phasing.md`, or a plan note named in the project map such as a phases plan), read it first, say whether the notes call it agreed, and propose revisions to it, with a change-history entry for each, instead of a fresh plan. Phase labels already in Linear belong to that plan. On a client-led project, an existing agreed plan stays the baseline, and every change to it is a proposal until the user records that the client accepted it.
3. **Capture, for each requirement group:** the client's stated priority (or MoSCoW tag), what it depends on (another group, a decision, an external party, an API or data input), the unknowns and risks, and any effort the notes state. Show stated effort only where the notes do not mark it internal or not for quoting; otherwise leave it out. Never estimate effort or set dates. Use dates only as the dates rule in step 5 allows.
4. **Propose the phase order from the data.** A phase is a slice of scope delivered in order, not a project stage: design, QA and launch are phases only when something depends on them. The number of phases follows the data, and a contract's own stage names are mapped to them, not copied. Work like this, and cite the rule letters in the table's "Why here" column (do not write a separate reasoning section): first pick the first phase with rule b; then order everything by rule a; within a dependency level use rule c; rules d, e and f then adjust where gated, uncertain or sign-off work sits. If the notes give no priority data (a build-order project may have none), skip rule c and say so.
   a. What other work depends on goes earlier.
   b. The smallest end-to-end slice of the journey that delivers value or a client handover goes first.
   c. The client's higher priorities (Must, high) before lower ones (Should, Could).
   d. Work that depends on an unconfirmed decision or an outside party is placed after it, or marked as gated with the gate named.
   e. High-uncertainty items get an early decision or spike gate, not a late surprise.
   f. Go-live, compliance and sign-off work comes last unless it gates something earlier.
   Tie-breaks: if a dependency (a) conflicts with priority (c), place the higher-priority item in the earliest phase its dependencies allow, and say so. A "slice" (b) is the smallest set of requirements that lets one user complete one core journey end to end; when the core journey is itself large, split it by journey step. A gate is a named decision listed under "Decisions that gate a phase" and named in the phase's "depends on"; a spike is work inside a phase, and becomes its own phase only if it blocks everything else.
   Dependencies come from the notes. When tickets exist, read their relations with `get_issue` (`includeRelations`) only for the tickets the plan needs, and say when a dependency is inferred from titles or parents instead.
   If the data does not support an order, say so and ask the PM the few questions the data cannot answer, most important first, and no more than five in chat at a time. The note's Open questions hold only what the PM cannot answer without dev; client answers are gates, and PM decisions are asked in chat and written in as answers. Offer alternatives only when the data supports two, and say what each is based on.
5. **Gates, risks, future scope.** Name each decision that gates a phase and who owns it. If the notes do not name an owner, write "owner not stated" and ask. List risks the notes support. Future scope holds only genuine nice-to-haves. Work the notes say is planned for later (not in this build) goes in a separate "Planned later" section. Never list exclusions. Contradictions between notes go in Open questions, and in Risks if they are material. Dates appear only where the client has them (for example in a client-facing roadmap) or the user states them, shown as stated, with the source, marked indicative when the document says so. Tentative dates like "about 22 Oct" are marked tentative. Never invent dates.
6. **replan only: label alignment.** Compare the plan with the phase labels on Linear tickets and with the newest notes (a later stand-up may have superseded the plan). Consider open tickets only (not Done, Canceled or Duplicate). Place each ticket in a phase from the plan note's own ticket lists, else by its epic or theme, and say when that was inferred. List drift: open tickets whose label disagrees with the plan, open tickets in a phase with no label, phase labels no plan row uses, and plan phases with no tickets. If the plan needs a new phase or renumbering, propose the label changes and ask before creating anything. Propose label changes; apply none. Read tickets with only the fields and labels you need, and follow the cursor while `hasNextPage` is true, or say the list covered only the first page.
7. **Status.** "Agreed" means: team-led, the user approves the plan; client-led, the user records that the client accepted it. A team-led plan is `committed` once agreed. A client-led plan is `proposed` until then. While `proposed`, create no tickets and no phase labels.
8. **Before showing:** check whether `<Project>/Scope and Phasing.md` already exists. If it does, show a diff against it, not a fresh note. Show the whole note in chat (see the sections below), with the status it will be written with (`proposed`, becoming `committed` on approval for a team-led plan) and the questions that remain. If `dry-run`, stop here and say nothing was written.
9. **Wait for a clear yes.** Then write `<Project>/Scope and Phasing.md` following `vault-update-rules.md` (frontmatter with the project tag (the folder name in kebab-case), `date` (ISO), `status`, `led-by` and `method` copied from the project map; wikilinks; plain hyphens). If the note exists, show a diff and mark superseded parts, never silently rewrite them. If this plan supersedes an older plan note (for example a 20 Oct phases plan), propose marking that note "superseded" with a link to the new one, as a separate diff shown first.
10. **Labels, only when asked and only for agreed phases.** Each application is a separate approved action (`save_issue` with the project's phase label; it prompts). A missing label is created only with approval. A project with no label scheme: ask before creating one, never invent names.
11. **Next step:** suggest `/roadmap`, then tickets via `/new-ticket` and `/tickets-from-updates`.

## Note sections
Status · Sources · Goal · Requirements by outcome (decided / proposed / unknown) · Phases (table: phase, what it delivers, why here, depends on) · Decisions that gate a phase · Risks · Future scope (nice to have) · Planned later · Open questions · Related. In replan mode add Label alignment. On a client-led project add Change history: one dated entry per revision, newest first, with the reason (the roadmap shows it). Omit any section that has no content, except Open questions, which says "None" when there are none. The first entry of a client-led Change history reads "first proposal" with the date and reason.

Never create, edit or label anything without a clear yes. Do not guess. End the chat summary with three short lines: **Read** (what you read and as of when), **Not read** (what you skipped and why) and **Could not check** (anything unavailable, including a search that covered only the first page).
