# /new-ticket

Creates ONE ticket. Arguments: `$ARGUMENTS` = a short description, optionally a project name, optionally `dry-run`.

Read these first: `.claude/project-map.md`, `.claude/reference/board-sweep.md` (the Todo rule and what counts as a blocker), `.claude/reference/ticket-rules.md` (including the Standing rulings). Follow them exactly. Credential notes in the project map are read only when the ticket needs credentials.

## Golden rule
Never touch a ticket in Done or QA (see `ticket-rules.md`). Do not set a Done or QA ticket as the parent, and do not add a relation to one. If the conflict check finds that a Done or QA ticket already covers the outcome, say so and stop; nothing is created or linked.

Only the PM's own tickets are edited (Ownership rule in `ticket-rules.md`). Read `createdBy` on any existing ticket the conflict check turns up. A ticket created by someone else is read-only: do not edit, comment on, relate or reparent it. Report the overlap to the PM, who decides whether the new ticket is still needed.

## Steps
1. **Project.** Work it out from the argument or the description. If it is genuinely unclear, ask one question. If Linear is not connected, stop and say so.
2. **Template.** Choose Standard, Epic or Design (UX design work for the Design Team, title `[DESIGN] - <what>`) using the rules in `ticket-rules.md`. Say which and why in one line. If unsure, ask one question. Epic-led by default: for a feature or a journey, suggest one rich epic and do not propose child tickets; devs break the epic into tasks. Create a single standard ticket when asked for one or when the change is one small thing a user can do.
3. **Read the template** from `Templates/Tickets/` (not from memory). A design ticket uses the Linear "Design Template Example", read with `get_template`, unless the PM asks for the long-form `design.md` (see Template choice in `ticket-rules.md`).
4. **Freshness sweep, then gather facts.** Do the sweep in `project-map.md` (fresh Linear, the latest Granola calls, Slack, newest notes) and also read the project's wireframe or design artifact and, for projects the map links as siblings, the sibling project's folder. Say what you read. If the ticket depends on something the client has not confirmed, hold it and say so (Standing rulings). Do not raise separate testing or audit tickets. If a vault note is stale against a newer source, say so. **Gather facts** from the project's start notes and the notes the description points to. Read only what you need. Do not ask for anything the notes already state. If the notes do not say it, it does not go in the ticket: use "N/A" for Blocked by and Waiting on, and "None" for Design, where they truly do not apply, or a genuine question under Open questions.
5. **Conflict check** exactly as in `ticket-rules.md`. **The conflict check always cross-references three groups in the same area: Done tickets, QA tickets and Backlog/To-do tickets.** Read each one's description in full (not titles), name the covering ticket, and classify the open ticket as built (propose closing it as Canceled, with a comment on the open ticket only), partly built (rewrite it down to what is missing), conflicting (state the conflict, never pick a side) or still needed. Done and QA tickets are read-only. See `ticket-rules.md`, Conflict check step 0. If a ticket already covers the outcome, show it and ask: update it (use `/update-ticket`) or skip. Never create a duplicate. If specs conflict, put the conflict in Open questions and draft the Linear comment for dev.
   Also decide the parent: if the notes or the conflict check show it belongs under an existing epic, propose that parent and ask the user to confirm. Run the Hierarchy check in `ticket-rules.md` on the proposed parent, its epic and its children.
   Before drafting, list the questions the PM can answer and ask them one at a time (see "Open questions" in `ticket-rules.md`). Only dev-dependent questions may stay in the ticket.
   Then ask the set-up questions (title, team and project, status, priority, labels, assignee, parent, blockers) as laid out in "Set-up questions" in `ticket-rules.md`. They are optional for the PM; do not draft until the PM has answered or skipped them.
6. **Draft** in the template's exact structure, product-focused: the user and client journey and the logic, no technical detail. Size the ticket to the change and write simple, user-focused wording like a proper product manager: short sentences, no jargon, Requirements as things a user can see or do (API tickets name the endpoints only). A ticket fits on one screen. Under Dependencies, `Blocked by:` lists open tickets only, each also set as a Linear blocked-by link (never a Done or QA ticket; never create a circular chain: check the proposed blocker's own blockers first). Client and partner decisions go under `Waiting on:`. Todo means certain (see `board-sweep.md`): raise a ticket in Todo only if a developer can finish it with no blockers AND it is definitely needed with final requirements. Anything waiting on a client or partner decision is raised in Backlog. If it is not needed soon, propose priority Low. Add the optional Credentials section only if the ticket needs it (see `ticket-rules.md`) and say in the summary that it does.
7. **Check.** Save the draft to a scratch file in the session scratchpad and run the check script as written in `ticket-rules.md`. A design ticket in the Linear format has no script kind: skip the script, apply the Quality bar by eye, and still run `get_issue` on every ticket ID in it. Fix every FAIL and rerun until it prints OK with no "NOTE: old template" line (that note means the draft used the wrong headings). The script also lists every ticket ID in the draft: run `get_issue` on each and replace any Done or QA ID with a plain description of the finished work.
8. **Show** the full text of the draft, not a summary, the check result, the team (DEV or DES), the project, the parent if any, the Hierarchy table, the Set-up table (status and priority with the one-line reason, labels, assignee, and who chose each), and any drafted comment. For a design ticket also show the labels (`Design` plus the paired dev ticket's phase label) and the assignee (the design team lead named in the project map), and send them with the create. If `dry-run` was given, stop here and say nothing was created.
9. **Wait for a clear yes.** Anything else is not approval.
10. **Create.** Re-run the check on the exact text, then call `mcp__claude_ai_Linear__save_issue` (this prompts; that is intended). Send the `## <title>` line's text as `title` and leave that line out of `description`, so the title is not printed twice in the ticket (see `ticket-rules.md`). Read the ticket back (`ticket-rules.md`, Hardening before any write, step 6) and report its ID, URL and the status, priority, labels, assignee and parent as returned. Post a drafted comment only if the user approved it.

Never create, edit or comment on a ticket without step 9. Do not set phase labels.
